🗄️ Pourquoi NoSQL (MongoDB) ?

🔄

Flexibilité du Schéma

Ajout de champs sans migration complexe. Évolution naturelle du modèle de données.

📦

Documents Embarqués

Historique des emprunts intégré. Pas de JOIN coûteux, une seule requête.

⚡

Performance Optimale

Application read-heavy. Lecture rapide avec embedded documents.

📊

Agrégations Puissantes

Pipeline d'agrégation MongoDB pour analyses complexes et statistiques.

📈

Scalabilité Horizontale

Sharding automatique pour croissance future de la bibliothèque.

💾

Snapshots Immuables

Conservation de l'historique même après modification/suppression des livres.

🔹 Opérations CRUD - Exemples

CREATE - Ajouter un Livre

def add_book(title, author, category):
    db = get_db()
    book = {
        "title": title,
        "author": author,
        "category": category,
        "total_copies": 5,
        "available_copies": 5,
        "added_at": datetime.utcnow(),
        "current_loans": [],
        "loan_history": []
    }
    result = db.books.insert_one(book)
    return result.inserted_id

READ - Recherche de Livres

def search_books(query):
    db = get_db()
    books = db.books.find({
        "$or": [
            {"title": {"$regex": query, 
                      "$options": "i"}},
            {"author": {"$regex": query,
                       "$options": "i"}},
            {"category": {"$regex": query,
                         "$options": "i"}}
        ]
    })
    return list(books)

UPDATE - Créer un Emprunt

def create_loan(user_id, book_id):
    db = get_db()
    # Update user: add to loans array
    db.users.update_one(
        {"_id": ObjectId(user_id)},
        {
            "$push": {"loans": {...}},
            "$inc": {"books_read": 1}
        }
    )
    # Update book: decrease available
    db.books.update_one(
        {"_id": ObjectId(book_id)},
        {"$inc": {"available_copies": -1}}
    )

AGGREGATE - Statistiques

def get_loans_by_category():
    db = get_db()
    pipeline = [
        {"$unwind": "$loans"},
        {
            "$group": {
                "_id": "$loans.book_snapshot.category",
                "count": {"$sum": 1}
            }
        },
        {"$sort": {"count": -1}}
    ]
    return list(db.users.aggregate(pipeline))

🔄 Comparaison Schémas - SQL vs NoSQL

❌ SQL - 7 Tables (Normalisé 3NF)

  • USERS - Informations utilisateurs
  • BOOKS - Métadonnées livres
  • CATEGORIES - Catégories de livres
  • LOANS - Table de jointure emprunts
  • BADGES - Badges disponibles
  • USER_BADGES - Table de jointure badges
  • USER_CATEGORIES_EXPLORED - Table de jointure catégories
7 Tables
Multiples JOINs
Foreign Keys

✅ NoSQL - 2 Collections (Dénormalisé)

  • users - Utilisateurs + loans embarqués + badges
  • books - Livres + current_loans + history

📦 Documents embarqués : Historique complet sans JOIN

💾 Snapshots : book_snapshot conservé dans loans

⚡ 1 requête : Toutes les données d'un utilisateur

2 Collections
Pas de JOINs
Embedded Docs

⚔️ Comparaison Requêtes - SQL vs NoSQL

Cas d'usage : Obtenir l'historique d'un utilisateur

❌ SQL - 3 JOINS Complexes
SELECT 
    u.username,
    u.email,
    l.borrow_date,
    l.deadline,
    l.status,
    b.title,
    b.author,
    c.name as category
FROM users u
LEFT JOIN loans l 
    ON u.id = l.user_id
LEFT JOIN books b 
    ON l.book_id = b.id
LEFT JOIN categories c 
    ON b.category_id = c.id
WHERE u.id = ?
ORDER BY l.borrow_date DESC;

❌ 3 JOINs = Opération coûteuse

❌ Données perdues si livre supprimé

❌ Performance dégradée avec volume

✅ MongoDB - 1 Requête Simple 
// UNE SEULE requête!
db.users.findOne({ 
    _id: ObjectId("user_id") 
})

// Résultat immédiat avec TOUT:
{
  "username": "Andro",
  "email": "andro@lib.com",
  "loans": [
    {
      "book_snapshot": {
        "title": "1984",
        "author": "Orwell"
      },
      "borrow_date": "2024-01-15",
      "status": "Returned"
    }
    // ... tous les autres emprunts
  ]
}

✅ 1 requête au lieu de 3 JOINs

✅ Snapshots conservés même si livre supprimé

✅ Performance optimale - pas de joins

⚖️ Avantages & Limitations NoSQL

✅ Avantages Majeurs

🚀

Performance de Lecture

  • Historique complet en 1 requête
  • Pas de joins coûteux
  • Données localisées ensemble
📸

Snapshots Immuables

  • Historique conserve infos originales
  • Livre modifié/supprimé = historique intact
  • Audit trail complet
💡

Simplicité du Code

  • Moins de requêtes à gérer
  • Pas de transactions complexes
  • Modèle orienté objet naturel
🔧

Flexibilité

  • Ajout facile de nouveaux champs
  • Pas besoin de migrations
  • Évolution rapide
📈

Scalabilité

  • Sharding horizontal automatique
  • Distribution géographique facile
  • Pas de limite d'utilisateurs

⚠️ Limitations à Considérer

💾

Duplication de Données

  • Snapshots dupliquent infos livres
  • Taille documents peut augmenter
  • Stockage plus important

✓ Acceptable pour historique complet

⏱️

Cohérence Éventuelle

  • Pas de garantie ACID multi-documents
  • Cohérence au niveau applicatif
  • Risque incohérence si update échoue

✓ OK pour notre cas (simple 1-to-many)

📏

Limite de Taille

  • Documents limités à 16MB
  • Problème si 1000+ emprunts
  • Solution: archivage périodique

✓ Improbable pour bibliothèque
